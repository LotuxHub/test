1. `epA()` bounded `off::EpOrig` by `.text` (`kTextRva + kTextMap`). In this
   build the stub entry lives in the `tempest` section at 0x9366004, i.e. past
   `.text` — the check always failed and the EP was never patched. Bound is now
   `kImageSize`, and each failure path logs its own reason.
2. `off::EpNew` from the dumper (0x5DE50C0) is a decoy stub
   (`lea rax,[.pexlat]; lea rax,[.pexlat]; ud2`). The real client main is
   **0x6EDC80**, the target of the `call` at `MAIN_CALL_RVA = 0x75056F`.

   has already run them; replaying them with `DLL_THREAD_ATTACH` faults inside
   the first callback. `Tls` is now `{0u}` on purpose.

## Wall reached: the static image has loader-filled "thunk graveyards"

credosdev publishes `payload.7z` (parts 1+2) for this build; extracted it is
`payload.bin`, 108,292,596 bytes = `.text` (0x6436000) + u64 `RtCount` (267817)
+ `.pdata` (0x3109EC). **Byte-compared against the decrypted exe text: 0
differences**, so it is the same static decryption, not a live dump.

That image still contains ~62 pages (≈250 KB) where Hyperion writes code at
load time: `cc`/`0f 0b` placeholders. First victim:

```
entry: calling client main at 0x6EDC80
entry: fault code=0xC000001D rva=0x5DE5260 bytes=00 00 00 00 0f 0b cc cc
```
`0x6EDC80` is `mov eax,0x2AD0; call 0x5DE5256; sub rsp,rax` — i.e. `__chkstk`,
whose real body is a placeholder (`66 66 0f 1f ... ; 0f 0b`).

Added `crtFix()` in `init.cpp`: it scans `.text` for `b8 <imm32> e8 <rel32> 48 2b
e0` and turns every such call target that starts with `0f 0b` into `ret`
(`rax` already holds the frame size, so `sub rsp,rax` still allocates). Result:
`crt: 1 chkstk thunks patched`, and the client main no longer raises an SEH
exception — it now exits silently, which is the shape of a Hyperion integrity
decision rather than a crash.

## 2026-11-21 - lua_Callbacks slot fix + executor thread re-sandboxed

### 1. `lua_Callbacks` was in the wrong order (real ABI bug)

`Module/Dependencies/Luau2/VM/include/lua.h` had the 0.747-era field order:

| slot | old (our header) | client 0.748 (velocity) |
|---|---|---|
| 0x08 | `panic` | `debugprotectederror` |
| 0x20 | `interrupt` | `panic` |
| 0x58 | `debugprotectederror` | `interrupt` |

The struct size (112) still matched, so the size-only `static_assert` never
caught it. Consequences at runtime, because our VM and the client share the
same `global_State::cb`:

- `GC_INTERRUPT()` (`lgc.cpp`) called the client's **panic** callback on every
  GC step (with the gc state passed as `errcode`).
- `resume_finish()` / `luaD_throw` paths (`ldo.cpp`) called the client's
  **interrupt** callback where `debugprotectederror` was expected, and vice
  versa. Roblox's interrupt callback is the script watchdog; invoking it at
  error-unwind points with a garbage `gc` argument can abort script
  environment setup, which matches the observed "LocalScript runs with missing
  globals" failures.

Fix: reordered the struct to the velocity 0.748 layout and added
`offsetof` static_asserts for all 14 slots so a future swap cannot build.

### 2. The executor thread had been un-sandboxed (regression)

`task_scheduler.cpp` had `luaL_sandboxthread(Shared::ExploitThread)` commented
out (the pristine tree in `.maintenance/original/` still has it enabled). That
made `Environment::initalizeEnvironment` write `_G`, `shared` and ~200 library
globals straight into the **client's** global table, which is shared with game
LocalScripts - they then saw a mutated/replaced environment.

Fix: `luaL_sandboxthread(Shared::ExploitThread)` re-enabled. It creates a
proxy globals table (`__index` -> the original gt), so the executor's globals
stay private and client globals are untouched. `ExecutionThread` already
sandboxes again per run and now chains through the executor proxy.

### Build

`Module/x64/Release/Module.dll`, 4,965,376 B, 0 errors (log:
`build-callbacks-fix.log`). Needs an in-game retest: join a place and check the
newest `%LOCALAPPDATA%\Roblox\logs\*Player_*_last.log` for

## 2026-11-21 (diag3) - staged fault reporting for the dispatch crash

### Symptom
With the callbacks fix + re-sandboxed executor thread, the first dispatch dies:

```
[Execution] Compiling 9942 bytes
[Execution] Loaded 7349 byte bytecode
[TaskScheduler] Script dispatch raised a memory exception
```

The executor never logs `Dispatched through task.defer`. The old handler threw
away `GetExceptionCode()`/`ExceptionAddress` and the stage, and because the
`__except(EXCEPTION_EXECUTE_HANDLER)` swallows the exception **without** running
C++ destructors, `g_StepHookMutex` (locked by `std::lock_guard` in `stepHook`)
stays locked and the module goes silent after the first fault.

### Changes (diagnostic build only)
1. `Module/RBX/diagnostics.hpp` (new): thread-local `Stage` + `Callback`
   breadcrumbs shared by the RBX layer and the vendored VM.
2. `execution.cpp`: the Lua half of `ExecuteScript` moved into
   `RunDispatchGuard()`, a POD-only function that wraps every step in a single
   `__try/__except` and records exception code, fault address and stage:

### Root-cause candidate: our Luau FFlags do not match the client
Stage 2 re-ran (pid 2920) and broke the client again at 6.5 s with the same
`GetService` / `ReplicatedStorage` nil errors, so the sandbox trigger is
reproducible.

While bisecting, the flag defaults in the vendored VM turned out to be
compile-time guesses:

  lstate.cpp  LuauBufferCage            = true   (hard-coded)
  lgc.cpp     LuauGcTraceUdata          = true   (hard-coded)
  lmem.cpp    LuauBufferSweep           = false  (LUAU_FASTFLAGVARIABLE default)
  lmem.cpp    LuauCageSplitData         = false  (default)
  lstring.cpp LuauSaltedInterningTable  = false  (default)
  lgc.cpp     LuauGcHeapShrinkFix       = false  (default)

The client runs one shared heap. LuauSaltedInterningTable decides which bucket
of global_State::strt a string goes into (salthash+hashshift vs lmod) and what
luaS_resize/luaS_free do; LuauCageSplitData decides whether a page's payload is
page->data or page->dataptr (lmem.cpp:1022); LuauBufferSweep changes page
recycling. With a wrong value our VM writes client objects with the wrong layout
and rehashes/unlinks interning entries in buckets the client never looks at.
That corrupts client name lookups and the page lists - exactly the symptom.

Evidence from our own logs: `pre-sandbox: raw task = nil` and later
`ClearInstanceFastPaths: game tag=-1` are name lookups against the client's real
global table, which does contain `game`/`task`. A bucket/pointer mismatch in the
interning table makes every short-string lookup miss.
